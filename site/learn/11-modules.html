Lesson 11

Modules

One statement, import "file.ql" as name, is the entire module system. No packages, no relative-dot imports, no export keyword to mark what's public — everything a file defines at the top level becomes visible through its alias.

Splitting a program across files

# mathutils.ql
let VERSION = "1.0"

pull square(x):
    return x * x

pull cube(x):
    return x * x * x
# main.ql
import "mathutils.ql" as mu

print(mu.VERSION)
print(mu.square(5))
print(mu.cube(3))

as name is mandatory — there's no bare import "file.ql" that dumps names into the current scope. Everything the imported file declared at its top level (variables and functions alike) hangs off the alias, accessed with ordinary dot syntax.

Path resolution

The path in import "..." is always resolved relative to the importing file's own directory, not the current working directory you happened to run quill from. That means a module can safely import its neighbors regardless of where the whole program gets invoked from.

What an import actually does

It's worth knowing this isn't a lightweight name lookup — import runs the target file as a completely independent program, from a fresh, empty global environment that starts out with only the built-ins (nothing from the importing file's own scope leaks in, and nothing the importing file has leaks out to it). Once that finishes, the alias is bound to a snapshot of everything the module declared at its top level.

Two things follow from that: first, a module has no visibility into the file that imported it — it's fully sandboxed apart from the built-ins every Quill file gets automatically. Second, since the snapshot is taken once, right when the import statement runs, anything the module would compute lazily or based on later state isn't an option — its whole top level runs immediately, top to bottom, exactly once.

Check yourself

  1. Is import "utils.ql" (no as) valid?

    No — as name is a required part of the syntax, not optional.

  2. If a.ql imports b.ql, can code inside b.ql see a variable that a.ql declared before the import line?

    No. b.ql runs against its own brand-new global environment, completely independent of a.ql's — the two files don't share scope in either direction.
