Lesson 9

Operator Overloading

A class can plug into Quill's own operators by defining a method with a special name — the same "dunder" (double-underscore) convention Python uses, so it should feel immediately familiar.

class Vec:
    pull init(x, y):
        self.x = x
        self.y = y
    pull __add__(other):
        return Vec(self.x + other.x, self.y + other.y)
    pull __eq__(other):
        return self.x == other.x and self.y == other.y
    pull __str__():
        return f"Vec({self.x}, {self.y})"

print(Vec(1, 2) + Vec(3, 4))     # Vec(4, 6)
print(Vec(1, 2) == Vec(1, 2))    # true

Two rules worth knowing

The overload only fires when the instance is the left-hand operand. There's no __radd__-style reflected operator (yet) — Vec(1,2) + 5 calls Vec.__add__ as usual, but 5 + Vec(1,2) never reaches it at all, because the dispatch only checks whether the left operand is an instance with a matching method.

The comparison dunders always come back as a real boolean. Even if __eq__ or __lt__ carelessly returns something else (a number, a string, nil), Quill coerces it through the same truthiness rules from Lesson 2 before handing it back through ==/</etc. — so a sloppy implementation can't leak a non-boolean value out through a comparison. Arithmetic dunders like __add__ are exempt from this, since their whole point is to return a new value, not a boolean.

Gotcha

A custom __lt__ makes direct comparisons (a < b) work, but it is not picked up by sorted() or .sort() — those compare elements at the Python level underneath the interpreter, which knows nothing about Quill's dunder-dispatch convention. Sorting a list of class instances with sorted() fails with "sorted() needs a list of all-comparable items," even if every element defines __lt__. If you need to sort custom objects, sort by an extracted plain value instead — for example, sorted(prices.map(pull(p): return p.amount)).

The default, if you define nothing

Exactly what Lesson 8 already showed: a class with no __str__ prints as <ClassName instance>, and == without a custom __eq__ falls back to identity — two separately-constructed instances are never equal, even with identical fields.

Check yourself

  1. Given the Vec class above, what does 5 + Vec(1, 2) do?

    It raises a runtime error ("cannot add number and Vec"), not a call to Vec.__add__. Overloads only trigger when the instance is on the left; there's no reflected-operator support.

  2. You define __lt__ on a Task class so t1 < t2 works. Does tasks.sort() now sort by that ordering?

    No. .sort()/sorted() don't go through Quill's operator dispatch at all, so a custom __lt__ has no effect on them — you'd get a "needs a list of all-comparable items" error instead.
