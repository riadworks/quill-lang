Lesson 8

Classes & Inheritance

Quill's classes are deliberately simple: no field declarations, no visibility modifiers, no static members — just methods, an implicit self, and inheritance, including multiple inheritance.

Defining a class

class Animal:
    pull init(name):
        self.name = name

    pull speak():
        return f"{self.name} makes a sound"

let generic = Animal("Creature")
print(generic.speak())    # Creature makes a sound

A class body may only contain method definitions (pull name(...):) — there's no way to declare a data field directly in the class body. Fields simply come into existence the first time you assign to self.somefield, almost always inside init.

init is the constructor: calling Animal("Creature") creates a new instance and immediately calls its init with those arguments. If a class has no init at all, it can only be constructed with zero arguments — passing any is a runtime error. self is never declared as a parameter; it's bound automatically inside every method.

Inheritance and super

class Dog(Animal):
    pull init(name, breed):
        super.init(name)
        self.breed = breed

    pull speak():
        return f"{self.name} the {self.breed} barks"

let rex = Dog("Rex", "Labrador")
print(rex.speak())     # Rex the Labrador barks
print(type(rex))     # Dog

class Dog(Animal): puts one or more parent classes in parentheses after the name. super.method(...) calls the ancestor's version of a method, and it resolves correctly no matter how deep the chain gets: each method remembers the class it was defined in, so super inside it always climbs from that class, regardless of which subclass's instance actually called it.

Multiple inheritance

Quill allows more than one parent class, exactly like Python: class Combined(Mixin1, Mixin2):. Method lookup and super both follow a Method Resolution Order (MRO) computed with the same C3 linearization algorithm Python uses. That matters most for a "diamond" — two classes sharing a common ancestor, both inherited by a third: 

class A:
    pull greet():
        return "A"

class B(A):
    pull greet():
        return "B->" + super.greet()

class C(A):
    pull greet():
        return "C->" + super.greet()

class D(B, C):
    pull greet():
        return "D->" + super.greet()

print(D().greet())    # D->B->C->A

D's MRO is [D, B, C, A]. Each super.greet() call resolves against the calling instance's full MRO, starting right after the class the current method was defined in — not just that class's own first parent. That's what makes A get visited exactly once here, in a consistent order, instead of the result depending on which branch (B or C) happens to be walked first. Listing the same base twice, or a base list with no consistent ordering, is a clear error the moment the class is declared.

Accessing fields and methods

rex.name           # "Rex" - field access
rex.speak()        # calling a method - self is bound automatically
rex.nonexistent    # RuntimeErr: 'Dog' has no field or method 'nonexistent'

type(instance) returns the instance's class name as a string (that's how print(type(rex)) above printed Dog, not some generic "instance" label).

Printing an instance

A class with no special handling prints as <ClassName instance>: 

print(generic)   # <Animal instance>

That's the default. The next lesson shows how to make a class print something actually useful.

Check yourself

  1. Where does a field like self.breed get "declared"?

    Nowhere, formally — there's no field-declaration syntax. It simply starts existing the moment something assigns to it, typically self.breed = breed inside init.

  2. If Cat extends Dog extends Animal, and Dog.speak() calls super.speak(), whose speak() does that reach — even when called on a Cat instance?

    Animal.speak(). super inside a method always resolves against the class that method was defined in (Dog), not the runtime type of the instance it was called on (Cat) — so it climbs exactly one level from Dog, to Animal, regardless of how far down the actual instance's class is.

  3. In the diamond above (D(B, C), both extending A), why does A.greet() only run once instead of twice?

    Because super resolves against D's single linearized MRO ([D, B, C, A]), not against each parent's own separate chain. B's super.greet() continues from wherever B sits in that MRO — landing on C, not back on A — so A is reached exactly once, after both B and C have run.
