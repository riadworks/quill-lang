Lesson 13

Networking

Quill ships its own tiny web server as a built-in — no framework required — plus two functions for making outbound HTTP requests. Together they're enough to build a real, working website.

Serving requests

serve(port, handler) starts a server on 127.0.0.1 (local machine only, not exposed on the network) and calls your handler function once per request. It blocks forever, so it's normally the last line of a script. 

pull handler(req):
    if req["path"] == "/":
        return "<h1>Welcome</h1>"
    return {"status": 404, "body": "not found", "content_type": "text/plain"}

serve(8080, handler)

Every request comes in as a single map with these keys:

KeyValue
method"GET", "POST", etc.
pathThe URL path, e.g. "/tasks" (no query string).
queryMap of parsed ?key=value query-string parameters.
formMap of parsed form fields, if the request body was application/x-www-form-urlencoded.
bodyThe raw request body, always as a string.
cookiesMap of cookies parsed from the Cookie header.

Your handler's return value becomes the response, in one of two shapes:

Return valueResponse
A plain stringStatus 200, that string as the body, text/html.
A mapstatus (default 200, or 302 if redirect is set), body (default ""), content_type (default text/html), redirect (sets the Location header), and set_cookie (a map of cookie name to value).

Building HTML by hand this way has no automatic escaping — run any user-supplied text through html_escape() (Lesson 12) before putting it in the response, or it's an XSS bug waiting to happen.

If a handler itself raises an error, the server doesn't crash and the visitor doesn't see the raw exception either — that request gets a plain "Internal Server Error" response, the real error is printed to the server's own stderr for you to see, and the server keeps running for the next request. A request body over 10 MB is also rejected outright (413) before it's read into memory, so a stray huge upload can't exhaust the server's memory.

Cookies

A cookie set through set_cookie goes out with HttpOnly (client-side script can't read it, which blunts session theft via XSS) and SameSite=Lax (blunts basic cross-site request forgery) by default: 

pull handler(req):
    if req["cookies"].has("session"):
        return f"welcome back, session {req["cookies"]["session"]}"
    let token = sha256(str(random()))
    return {"body": "logged in", "set_cookie": {"session": token}}

serve(8080, handler)

There's no Secure flag on that cookie, deliberately — this server only ever speaks plain HTTP, and a Secure cookie would simply never be sent back to it.

A form handler

pull handler(req):
    if req["method"] == "POST" and req["path"] == "/add":
        let title = req["form"]["title"]
        # ... save it ...
        return {"redirect": "/"}      # 302 back to the homepage
    return "<form method=\"POST\" action=\"/add\"><input name=\"title\"></form>"

serve(8080, handler)

Making outbound requests

FunctionDoes
http_get(url) / http_get(url, headers)A GET request.
http_post(url, body) / http_post(url, body, headers)A POST request. body can be a map (form-encoded automatically) or a plain string.
url_encode(s)Percent-encodes a string for safe use inside a URL.

Both request functions return the same shape, and raise a clear error rather than crashing if the host is unreachable:

let res = http_get("https://example.com/api/status")
print(res["status"])    # e.g. 200
print(res["body"])      # response body, as a string

let created = http_post("https://example.com/api/items", {"name": "widget"})
# body is a map here, so it's form-encoded automatically with the right Content-Type

Check yourself

  1. What does returning a plain string from a serve() handler produce?

    A 200 response with that string as the HTML body.

  2. What does {"redirect": "/login"} returned from a handler do?

    Responds with status 302 (the default when redirect is present) and a Location: /login header, sending the browser there.
